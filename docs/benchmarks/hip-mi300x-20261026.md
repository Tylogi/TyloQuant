# Retained MI300X HIP inference measurements

The native HIP runtime executes compressed RTRELL05 TQ rows directly for
expert decode and through transient LDS tiles for MFMA prefill. The optimized
path includes fused Gate/Up/SwiGLU, routed Down/reduction, expert placement,
shared-expert and GR fusion, wave64 GDN/convolution, and DSV sparse attention,
index selection, mHC and MXFP8 projection. Weights remain compressed at rest
on the GPU. Engram tables retain their CPU range readers.

## Real DeepSeek-V4.1-Flash-1017 Q3

These are retained whole-model measurements, taken before the final operator
optimizations below. They are not a new run of this PR's checkout.

Two MI300X devices (the same physical devices 5 and 7 for both programs), one
request, F16 KV, MTP and prefix reuse disabled, 128 output tokens, one warmup
and three measured repetitions. Rates are medians in tokens/s.

| Prompt | TQ Q3 EP2 PP | llama.cpp UD-Q2_K_XL TP2 PP | TQ decode | llama.cpp decode |
|---:|---:|---:|---:|---:|
| 2048 | 6041.89 | 684.34 | 70.14 | 45.98 |
| 4096 | 6736.42 | 682.05 | 69.80 | 46.06 |

The models contain real quantized weights. TQ Q3 and Unsloth UD-Q2_K_XL have
different payloads and precisions, and EP and TP distribute work differently.
Native prefill compute chunks contain 2048 tokens; llama.cpp uses batch 2048
and microbatch 512. These results do not establish equal model quality.

The llama.cpp baseline is commit `2280f0fd163b03d4331d49e08460f66502e35854`.
Its retained loading-only changes allocate at least 256 tensor metadata slots
and pack eligible H2D transfers; inference kernels are unchanged by those
local adjustments. The saved baseline was reused, not rerun for publication.

These use saved real compressed experts or saved sparse-attention fixtures
on one MI300X, matching each operator's input, warmups and repetitions.
They have not been extrapolated into a whole-model throughput claim.

|---|---:|---:|---:|

Expert outputs and sparse-attention outputs were bit exact in these retained

The source release retains the accepted implementations and their runtime

## Qwen3.8-Flash-Next prefill follow-up (2026-10-26)

These measurements use GPU 5 on the same MI300X host, the random compressed
4.507989 bpw column-scale fixture, 2,048 tokens, one warmup and the median of
three profiled repetitions. Each run loads and executes one native decoder
block. Profiler overhead is included. They are not whole-model PP/decode rates.

| Native block | Before (ms) | Verified after (ms) | Latency reduction |
|---|---:|---:|---:|
| GDN block 0 | 10.82784 | 8.69362 | 19.7% |
| PLE + GDN block 1 | 26.99338 | 16.96087 | 37.2% |
| QSA block 3 | 16.49224 | 8.85483 | 46.3% |

All after rows use the final source version, including CPU-mapped PLE, GR,
GDN preparation and recurrent prefetch, QSA fusions and the two enabled direct
TQ projection shapes. These are separately measured blocks, and must not be
added or extrapolated into a whole-model rate. Source-runtime artifact:
`qwen38-pp-20261026/summary.json`; final raw profile:
`qwen38-pp-20261026/block-profile-final-direct-prefill.log`.

GR's existing BF16 injection reduction and sigmoid now cover prefill; the
2,048-token standalone call measures 657.96 to 78.02 microseconds. GDN's
convolution, Q/K normalization and decay/beta preparation now reach the existing
prefill kernels instead of a short-sequence-only entry. The FP32 recurrent core
stages 16 tokens in shared memory: 1.36409 to 1.29178 ms in the paired operator
measurement, with identical output and final-state values. State updates remain
mathematically recurrent.

QSA's dense branch now uses the native causal MFMA implementation. Its normal
forward also uses the grouped projection and normalization/RoPE path previously
connected to graph execution, skips unused index queries below the sparse
budget, and connects the existing gate and pooled-key normalization fusions.
Cached K/V were already FP16 through `SequenceCache::append` before this work;
the uncached path now consistently uses that type too. The attention kernel's
operand/reduction behavior follows the existing optimized sparse path. Comparing
the previous and final QSA paths on the same inputs gives relative L2 errors
6.95e-6 for a 257-token dense call and 4.70e-5 for a subsequent 2,048-token call
crossing the 2,048-token sparse budget.

PLE tables remain on the CPU. Requested compressed ranges are copied from a
retained read-only CPU file mapping instead of repeated seek/read calls; no
whole-table GPU allocation or expanded-weight cache is added. In the paired
block profile the PLE segment measures 16.29 to 8.86 ms with warm file pages.
This does not establish cold-storage performance.

Ordinary direct-compressed TQ prefill is enabled for FP32 subgroup weights on
gfx942 at M=2048, K=2560 and N=6144 or 12288. The GDN Gate projection measures
635.59 to 572.10 microseconds (1.111x); QSA Query measures 1183.38 to 1101.92
microseconds (1.074x) against the native transient-materialization caller.
The kernel reconstructs small weight tiles in shared memory and accumulates
with FP32 MFMA. Its workspace holds only scaled activation high/low half
components and per-row power-of-two scales. It does not cache expanded weights.
The two-component representation introduces relative L2 projection error near
1.02e-6. Exceptional rows with nonfinite or extreme magnitudes compute directly
from the original FP32 input; checked NaN/Inf classifications agree with the
old path, and the large/tiny finite checks have relative errors below 3.3e-7.

Other ordinary projection geometries retain their previous native dispatch;
this does not replace all transient materialization or establish that every
projection is optimized. Slower MFMA, split-K, persistent-tile, codebook-lookup
and chunked-state prototypes are excluded. No additional whole-model,
llama.cpp or fake-model MTP benchmark was run for this follow-up.

## CPU-batched PLE prefill (2026-10-26)

PLE tables remain compressed in their read-only CPU file mappings. Ordinary
prefill at 128 or more tokens now reuses a bounded row packet for the current
request shape, deduplicates the requested IDs, uploads the populated portion
once and executes one row-decode kernel. No whole-table GPU cache is added.
Row preparation writes standard RTRELL05 rows into caller-owned storage,
avoiding temporary per-row vectors and repeated layout parsing. Only readers
known to use independent memory mappings may prepare large unique selections
on four CPU workers; HIP operations stay on the caller thread.

The packet fences its prior stream consumers before reuse, and its returned
activation tensor is cloned so a later upload cannot overwrite a prior result.
Shape, device or stream changes replace the workspace. Short decode retains
its previous row lookup/graph path. This adds no model-state or session cache.

On GPU5, 2,048-token hashing selects 32,768 embedding rows across 128 shards.
The following medians include CPU preparation, transfer and GPU completion,
with warm mapped pages and an already allocated request workspace:

| Prompt IDs | Previous row pipeline (ms) | Batched pipeline (ms) | Speedup |
|---|---:|---:|---:|
| Periodic tokens | 7.548 | 0.800 | 9.43x |
| Random tokens | 18.772 | 3.864 | 4.86x |

The production PLE+GDN block-1 profile, one warmup and median of three runs,
falls from 16.96087 to 10.54868 ms (37.8% less
latency). Its PLE segment falls from 8.48162 to
1.81032 ms. These timings include profiler overhead.
Row outputs match the previous lookup bit for bit, including varied IDs,
duplicates and shard boundaries. The focused format check also covers selector
parity and column scales. Numerical and raw profile evidence is retained in
`qwen38-pp-20261026/ple-batched-prefill-summary.json` and the corresponding logs.

No whole-model benchmark was run after this PLE change. The preceding
whole-model result at TyloQuant commit `244dcc8` remains 4,829.00 PP / 71.09
ordinary decode tok/s at 2K, and 4,697.14 / 71.01 at 8K. That GPU5 result uses
the random 4.507989 bpw fixture, one global request, 256 output tokens, FP16 KV,
MTP and activation Q8 disabled, 2K compute chunks, one warmup and three timed
repetitions. The reused llama.cpp commit
`31288c9c66e59377f7788d920678a565bb89dd37` baseline is 2,598.03 / 65.35 at 2K
and 2,595.02 / 63.39 at 8K, using real UD-Q4_K_XL weights on GPU7. The GPU and
format differences prevent treating this as a strictly same-device or
quality-equivalent comparison. The new PLE gains are not extrapolated into
those whole-model rates. A tested 32x32 MFMA projection variant was slower and
is excluded from both PRs.

## Ordinary TQ prefill LDS layout (2026-10-26)

The direct-compressed FP32 prefill kernel now selects its four-half LDS
vectors using row-index bits 1..3 in the XOR address swizzle. This changes
storage addresses while retaining the same decoding and MFMA arithmetic.
The native default dispatch additionally enables the measured QKV geometry
M=2048, K=2560, N=10240. Gate and Query keep their existing direct dispatch.
Only bounded activation workspaces and LDS weight tiles are used.

Native caller measurements on GPU5 compare the new default against the
previous transient-materialization + BLAS caller in the same process:

| Projection | M / K / N | Previous caller (us) | Direct compressed (us) | Speedup |
|---|---|---:|---:|---:|
| Gate | 2048 / 2560 / 6144 | 638.52 | 545.00 | 1.172x |
| QKV | 2048 / 2560 / 10240 | 1014.42 | 971.78 | 1.044x |
| Query | 2048 / 2560 / 12288 | 1181.31 | 1035.17 | 1.141x |

Relative L2 projection errors are approximately 1.02e-6. The focused GDN
comparison changes only the QKV projection and checks the 2K forward plus a
subsequent ordinary decode token. Relative errors are 2.13e-6 for prefill
output, 1.01e-6 for convolution state and 1.65e-6 for recurrent state; the
subsequent output is 1.96e-6. Other projection shapes retain prior dispatch.

The separately profiled production GDN block0 and QSA block3 measure
8.55095 and 8.69427 ms respectively. These small block-level changes do not
establish a new whole-model rate. The large PLE result above was measured at
the preceding CPU-batched PLE commit. No whole-model or llama.cpp run follows
this layout update. Evidence: `qwen38-pp-20261026/bank-prefill-summary.json`.

The 32x32 MFMA, wider-N tile and fixed-bit row-grouping variants were slower
and are excluded. Increasing the PLE CPU workers from four to eight did not
give a clear additional benefit; the published implementation retains four.
